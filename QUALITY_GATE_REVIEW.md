\# Quality Gate Review



\## Finding 1 — Reliability / Accuracy



What I found:

The first POST test using curl.exe in PowerShell failed because the JSON request body was not passed correctly.



How I fixed it:

I used PowerShell Invoke-RestMethod with a JSON body generated by ConvertTo-Json.



Evidence:

POST /api/bookings successfully created a booking with HTTP 201.



\---



\## Finding 2 — Business Rule



What I found:

The system must prevent overlapping bookings for the same equipment.



How I fixed it:

I implemented an overlap check using:



newStart < existingEnd

AND

newEnd > existingStart



The check is applied to both POST and PATCH.



Evidence:

An overlapping booking returned HTTP 409.



\---



\## Finding 3 — Security / SQL



What I found:

Request data must not be concatenated directly into SQL queries.



How I fixed it:

I used prepared statements with parameter binding through .prepare() and .bind().



Evidence:

Equipment IDs and booking IDs are passed through bound parameters in the API implementation.



\---



\## Finding 4 — Reasoning / You Own It



What I found:

The API needs clear HTTP status codes so that clients can distinguish successful requests from validation and conflict errors.



How I fixed it:

I used:

\- 200 for successful GET/PATCH

\- 201 for successful POST

\- 204 for successful DELETE

\- 400 for invalid input

\- 404 for missing resources

\- 409 for booking conflicts



Evidence:

The API tests verified these response cases.
